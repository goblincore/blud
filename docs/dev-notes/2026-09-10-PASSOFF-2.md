## 2. NEXT ACTIONS, in the order the evidence supports

### 1. The march: MEASURE THE STEP AXIS BEFORE PULLING ANY LEVER

Every march lever in this repo's history died on an assumed axis, and the shipped
configuration shows why the easy ones are gone:

| lever | state |
| --- | --- |
| under-relaxation 0.6 → 1.0 (plain sphere tracing) | **BANKED** — `GAME_OMEGA = 1.0`; the game runs the fbm shell amp at 0, so the field is conservative and 1.0 is *exact* as well as faster |
| over-relaxation (omega > 1) | **DEAD** — the relaxed tracer path produced the 2026-08-31 box washes and ships off |
| near-wound step 0.6 → 1.0 | **BANKED** — `GAME_WOUND_STEP`, owner look 2026-09-05 |
| last-step secant accept | **BANKED** — `GAME_LAST_STEP = 4`, room 1 11.92 → 10.17 ms |
| footprint AA at range | **BANKED** — `GAME_AA = 1.0` |
| step budget / miss-pixel tail | **DEAD** — a 6× cut produces no monotonic trend ("per-step is not the axis") |
| quarter-res depth prepass | **DEAD BY OWNER LOOK** — flipped on for one look pass and reverted the same day: the geometry deletion it warned about was "very noticeable". `GAME_DEPTH_PREPASS = 0`, with a census gate required before any retry |
| cone pre-pass | **DEAD** — the documented −22% does not reproduce; also reproduces a CPU submission stall |
| deeper interlace h/3, h/4 | **DEAD on look** (structural, not tuning) |

**A MARCH-OCCUPANCY INSTRUMENT ALREADY EXISTS, AND IT CANNOT PRICE THE WASTE.**
`__sdfGame.occupancy()` (march debug mode 4: the target's channels become
r=steps, g=hit, b=rasterised, a=t for one frame) is the seam that was supposed to
answer this, and `scripts/sdf-march-occupancy.{mjs,sh}` now drives it across the
five rooms in the walk and post-burst states. Run 2026-09-10, the numbers are
internally inconsistent, and the reason is in the shader's own comment:

| room (state) | coverage | occupancy | rasterised | hits |
| --- | ---: | ---: | ---: | ---: |
| 1, 2 (walk/burst) | 0.0% | 0.0% | 0 | 0 |
| 3 (walk/burst) | 1.7% | 0.0% | ~4.1k | 0 |
| 4 (walk/burst) | 12.3% | 0.0% | ~29.5k | 0 |
| 5 (walk/burst) | 5.4% | **74.3%** | ~12.9k | 9.5k |

Rooms 1/2 with `rasterised 0` are legitimate (a room-centre pose facing a wall —
`teleport` puts the player at the centre with yaw 0, and `bodiesOnScreen` counts
actors in the ROOM, not in frame). What is NOT usable is **rooms 3/4 reporting
29,588 marched pixels and ZERO hits**, and a mean of **1.0 steps** on the miss
rays. Mode 4 is definitely active (a normal render does not have zero pixels with
green > 0.5 across 29k body-box pixels, and channel 2 is exactly 1.0 by
construction). The cause is the bias `march.wgsl.ts` already documents at the
mode-4 return: **it returns BEFORE the discard, so a ray that gave up still writes
depth** — at the distance it gave up, which inside a proxy box is NEARER than the
real surface. The near-miss fragment therefore wins the depth test and the
readback reports "no flesh" for a pixel the shipping render draws. Where proxy
boxes overlap (three bodies in a room, i.e. the interesting case) the hit count
collapses toward zero and `occupancy()` becomes a restatement of its own caveat.

**So `occupancy()` prices nothing in the rooms that matter, and the step channel
reads 1.0 for those fragments** (a ray that starts inside the box, finds nothing
and exits in one step). Fixing it means writing the hit flag from the
POST-discard path (or comparing the mode-4 buffer against the shipping render's
own coverage) — a small, contained change to the debug return, and the
prerequisite for ANY pixel-waste number on this march.

So: **the missing measurement is a per-pixel STEP-COUNT HISTOGRAM** — and, before
it, an occupancy reader that is not defeated by overlapping proxy boxes. Nothing in
the repo says whether the march's time is (a) a broad mass of pixels at moderate
step counts — in which case the term to attack is the per-step FIELD EVAL, not the
loop; (b) a small tail walking very far — then accelerate those specifically; or
(c) mostly per-pixel FIXED cost — then stop touching the loop at all. The march
already carries a steps budget (`marchCfg.x`) and the readback machinery for
debug buffers exists (`frame-hash.ts`, `demoHash`'s layers). This is a contained
instrument and it is the honest prerequisite for any further march work.

⚠ **A STALE MEMORY TO IGNORE:** the dualmem context for this project claims "a
quarter-resolution depth prepass was adopted and merged to main; it roughly halves
the SDF ray walk". The CODE says the opposite (`GAME_DEPTH_PREPASS = 0`, reverted
after an owner look pass found visible geometry deletion). Verify memory against
the code.

### 5. The CPU side — the term that scales with what comes next

Room 4's frame is ~14 ms with ~9.3 ms labelled GPU; the two top-level CPU
segments are `cpu:tick` ~5.0–5.5 ms and `cpu:draw` ~3.0–3.7 ms, i.e. comparable
to the whole GPU. `cpu:phase:*` rows are SUB-phases (wound-hit reads 5–7 ms in
room 4's fire/gib segments) — **I did not establish how they compose with
`cpu:tick`, so do not add them up**; read the bench's CPU attribution rules first.
The point for planning: the march is ~6–7 ms of a ~14 ms frame, and the CPU terms
are the ones that grow with particles, wounds and actors — exactly the direction
the owner says the game is heading ("there will be more lights and particles").

## 4. Traps — the previous seven, plus what this session added

The previous pass-off's seven still stand (read the console at load; no backticks
in WGSL template literals; `BENCH_LEGS` naming a missing leg silently measures
`baseline`; a cross-boot hash comparison is never evidence; an absurd diagnostic
value means the READER is broken; a confident wrong verdict in a tool is worse
than no verdict). This session added four:

1. **A `wgslFn` kernel with a `workgroupBarrier` must NOT be given a numeric
   dispatch count.** three then emits `if (instanceIndex >= count) return;` ahead
   of the call and Tint rejects the barrier behind that guard. Dispatch by an
   explicit WORKGROUP array instead — and there must be no count guard in the
   kernel either.
2. **A readback without a GPU fence belongs to the PREVIOUS dispatch.** The
   gather rig read eight lights' worth of layer from a rung that had just set
   zero, and one rung returned another's digest byte for byte. `resolveGpu()`
   after the step, before the read (`demoScenario` does this before every hash).
3. **The interlaced march HOLDS rows from the previous frame**, so a capture
   taken right after a parameter change is a mix of two settings (measured: a
   448k-pixel "noise floor" with a bit-identical probe layer). Step 8 frames —
   four field cycles — after any change you intend to photograph.
4. **A cross-boot PIXEL diff measures the two-state branch, not your change.**
   Two gain-0 boots agreed bit-for-bit in the probe layer and differed in 27.6% of
   the frame's pixels. For anything subtle, do the A/B IN ONE BOOT.
