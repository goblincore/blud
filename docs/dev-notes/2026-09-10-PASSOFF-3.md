## 3. LIKED BUT UNSPECCED — per-object motion blur

Owner, verbatim: *"I like the smearing effect but applied selectively in a way that
looks like per object motion blur"*, and then, after the full-sharpness A/B: *"I
like it but I don't like that its trapped within the body. its like the frames
accumulate within the silhouette of the body ... i just like having some smear
during certain movements."*

**That is a precise spec complaint, and it names the two things missing:**

1. **A FORWARD warp, not a backward fetch.** The current pass reads the history at
   the camera-predicted position, so with a static camera it samples the SAME pixel
   and stacks the body's past appearances inside its current silhouette. Real
   motion blur displaces the PAST body along its own velocity so the trail spills
   onto the background it has left. Camera-only reprojection cannot do that; it
   needs per-object velocity.
2. **Flesh outside the current silhouette must be allowed.** The resolve currently
   blends only where the CURRENT frame has a surface (an explicit guard, added to
   avoid painting stale bodies over the background). That guard is exactly what
   traps the smear. It has to become a validity test (reprojected depth in front of
   the background) instead of a coverage gate.

Also required: **per-object velocity must cover the MESH parts** (skeleton, armor,
viewmodel policy decided), not just the marched flesh — otherwise bone and flesh
smear differently, which is the same defect class as the old held-row bone/flesh
disagreement. Vertex data is close to hand (`bone-instancer.ts` packs posed
instances per frame); a screen-space motion field still needs its own pass and
target.

**Costs, honestly:** the march scale stays at the shipped value (no reconstruction,
so "too blurry" cannot happen and the jitter is not wanted), but a full-resolution
float history has real bandwidth — and the owner reports *"the performance really
tanks"*, which the code explains: the ping-pong is a `copyTextureToTexture` of a
full-res RGBA32F buffer (~16 MB/frame) that is **not a labelled pass**, so it is
invisible to the 0.05 ms pass row quoted earlier. Price the copy before trusting any
cost figure here; swapping bindings for the copy is the likely fix.

## 6. TRAPS THIS SESSION PAID FOR (on top of PASSOFF-2's eleven)

1. **A quad sampling `uv()` writes with the OPPOSITE Y origin to the texture's texel
   rows.** My resolve mirrored the flesh ("bodies walking on the ceiling"). The repo
   had already paid for this once — the field ring's retention had to become a true
   texture copy for the same reason. A blend cannot be a copy, so it must take the
   shared `flipY` convention, never a hard-coded mirrored index.
2. **A gate inherits the blind spots of its framing.** My convergence gate staged a
   vertically CENTRED subject, where a Y flip is invisible to a difference metric —
   so it converged beautifully while the body was upside down.
3. **Do not compare an anti-aliasing estimate against a single aliased reference.**
   Against the unjittered scale-1.0 render the accumulation looks like a catastrophe
   (5.8 vs 0.5); against a converged full-scale accumulation it converges. The first
   reference is one aliased sample, and removing aliasing must read as "further away".
4. **Backticks inside a WGSL template literal** — third occurrence in this repo, and
   it was my own explanatory comment. There is now a guard snippet for it.
5. **Write the GAME's state, not the layer's.** `sdfLayer.setScale()` left the game's
   `sdfScale` at 1.0 and something re-applied it, so `?accumscale` booted at 1.0.
6. **A `copyTextureToTexture` is not a labelled pass**, so pass timing cannot see it —
   which invalidated one of my own cost claims.
7. **A CDP `addScriptToEvaluateOnNewDocument` hook can outlive the rig that added it**
   in a reused Chrome, and a page caught mid-HMR-reload has `__sdfGame === undefined`
   for a moment. Both cost real debugging time on a *verification* script, not on the
   game.
